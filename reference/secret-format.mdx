Standard Webhooks supports two secret formats. You can use a `whsec_<base64>` prefixed secret — the format defined by the Standard Webhooks specification and used by platforms like Svix — or a plain UTF-8 string used directly as HMAC key bytes. Both formats are accepted everywhere a secret is expected: `signing.secret` in `WebhooksConfig`, `Subscriber.secret`, and the `secret` argument to `createVerifier()`.

---

## `whsec_<base64>` format

The `whsec_` format is the Standard Webhooks canonical secret format. The prefix acts as a type tag, and the remainder is standard base64 (RFC 4648, with `+` and `/`, padded with `=`). When used, the library strips the prefix and base64-decodes the remainder before using the raw bytes as the HMAC-SHA256 key.

```text
whsec_dGhpcyBpcyBhIDMyIGJ5dGUgc2VjcmV0ISEhISEhISE=
│──────│──────────────────────────────────────────│
prefix        base64-encoded key bytes
```

For interoperability with other Standard Webhooks implementations, prefer this format. A secret generated by another tool (Svix CLI, a dashboard, `openssl`) will work as long as it starts with `whsec_` and has valid base64 after the prefix.

### How to generate a `whsec_` secret

Generate 32 random bytes, base64-encode them, and prepend `whsec_`:

```bash
echo "whsec_$(openssl rand -base64 32)"
```

Or in Node.js / Bun:

```ts
import { randomBytes } from "node:crypto";

const secret = "whsec_" + randomBytes(32).toString("base64");
```

The 32-byte length is a recommendation — any key length accepted by WebCrypto's HMAC-SHA256 (at least 1 byte) is technically valid, but 32 bytes (256 bits) provides a comfortable security margin.

### Validation rules

For a `whsec_` secret to be valid:

1. It must start with exactly `whsec_` (case-sensitive).
2. The remainder must be valid standard base64: length divisible by 4, characters in `[A-Za-z0-9+/]`, up to two `=` padding characters.
3. The decoded bytes must be non-empty.

An empty suffix (`whsec_` with nothing after it), invalid base64 characters, incorrect padding, or a zero-length decoded result all make the secret invalid.

## Plain UTF-8 string format

Any non-empty string that does not start with `whsec_` is treated as a raw secret. The string is encoded to UTF-8 bytes and those bytes are used directly as the HMAC key — no decoding step occurs.

```ts
const verifier = createVerifier("my-raw-signing-secret");

const wh = webhooks({
  events,
  subscribers,
  signing: { secret: "my-raw-signing-secret" },
});
```

This format is convenient for development and simple integrations where you control both the sender and the receiver. Any non-empty string works.

<Warning>
  If you store a base64 string without the `whsec_` prefix, it will be used as raw UTF-8 bytes — not decoded. A sender using `whsec_<same-base64>` and a receiver using the bare base64 string will compute signatures over different key bytes and verification will always fail. Be consistent: either use the `whsec_` prefix on both sides, or use a plain string on both sides.
</Warning>

## Validation: `isValidSecret(secret)`

The `isValidSecret` function lets you validate a secret before storing or using it. It returns `false` for any input that would cause `send()` to return an error or `createVerifier()` to throw.

```ts
import { isValidSecret } from "@webhooks/sdk";

isValidSecret("whsec_dGVzdA==");  // true  — valid whsec_ with non-empty base64
isValidSecret("my-secret");        // true  — valid plain string
isValidSecret("whsec_");           // false — whsec_ with empty suffix
isValidSecret("whsec_!!!bad!!!");  // false — whsec_ with invalid base64
isValidSecret("");                 // false — empty string
```

Use `isValidSecret` to validate user-supplied secrets in your configuration UI or onboarding flow before persisting them. A secret that fails this check will cause every `send()` to that subscriber to fail with an error.

## Error behavior

The library enforces secret validity at two different points depending on the code path:

- **`send()` returns `err(...)`** — If `send()` resolves subscribers and one of them has an invalid signing secret (either no secret at all, or a `whsec_` secret with invalid base64), `send()` returns `{ ok: false, error: "invalid signing secret for subscriber <url>: ..." }`. No HTTP request is made. This means a single misconfigured subscriber blocks the entire event.

- **`createVerifier()` throws `RangeError`** — If you pass an invalid secret to `createVerifier()`, a `RangeError` is thrown immediately at the call site. This is intentional: a broken deployment fails at startup rather than accepting requests with a known-invalid key.

```ts
// send() — error as value
const result = await wh.send({ event: "invoice.paid", subject: "acct_1", data });
if (!result.ok) {
  // result.error might be "invalid signing secret for subscriber https://..."
}

// createVerifier() — throws immediately
try {
  const verifier = createVerifier("whsec_"); // RangeError thrown here
} catch (e) {
  console.error(e.message); // invalid webhook secret: ...
}
```

## Per-subscriber secrets

The top-level `signing.secret` in `WebhooksConfig` acts as a default. Individual subscribers can carry their own `secret` field, which takes precedence over the top-level default. This lets you give each subscriber a unique secret for credential rotation, multi-tenant isolation, or compliance requirements.

```ts
const wh = webhooks({
  events,
  signing: { secret: process.env.DEFAULT_WEBHOOK_SECRET! }, // fallback
  subscribers: async ({ subject }) => {
    const subs = await db.query.subscribers.findMany({ where: eq(t.subject, subject) });
    return subs.map((s) => ({
      url: s.endpointUrl,
      secret: s.webhookSecret ?? undefined, // per-subscriber secret when set
    }));
  },
});
```

When a subscriber has no `secret` and there is no `signing.secret`, `send()` returns an error for that subscriber. Always ensure every subscriber can be resolved to a secret.

## Interoperability with Svix

`@webhooks/verify` accepts both `webhook-*` and `svix-*` header names. This means you can use it to verify webhooks sent by Svix senders without any changes — the `svix-id`, `svix-timestamp`, and `svix-signature` headers are treated identically to their `webhook-*` counterparts. The same `whsec_<base64>` secret format is also shared with Svix, so a secret generated by the Svix dashboard will work directly with `createVerifier()`.

<Note>
  The interoperability goes one way: `@webhooks/sdk` always sends `webhook-*` headers (the Standard Webhooks canonical names). If your consumers use a Svix-specific client that only reads `svix-*` headers, they would need to update to a library that also accepts `webhook-*`, or you could open a compatibility issue with that client.
</Note>
